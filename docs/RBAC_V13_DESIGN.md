# تصميم RBAC لعدة مستخدمين + خطة الترحيل الذرّي v12→v13

> **المهمة:** T24 (مسار WS-F) من خطة الموجة W1 — أسبوعا 8–10 · **الحالة:** تصميم معتمد بانتظار اعتماد CTO
> **التاريخ:** 2026-10-03 · **المؤصِّل:** كيانات v12 الفعلية (25 كياناً في `data/db/Entities.kt`) · نظام الحماية القائم (`PinVault`/`LockoutGuard`/`BiometricGate`) · سجل فجوات ZATCA-2 (الترحيل المشترك v13)

---

## 1) لماذا RBAC الآن — والسؤال الحقيقي: على أي جهاز

الطلب القادم من مسار المؤسسات (WS-F في الخارطة) هو «صلاحيات لكل مستخدم»: أمين الصندوق يبيع ولا يرى الأرباح، والمحاسب يرى التقارير ولا يعدل الأسعار، والمالك يرى كل شيء. لكن قبل رسم مصفوفة صلاحيات لا بد من الإجابة عن السؤال المعماري المحدد للنطاق: **SuperBiz تطبيق جهاز واحد متعدد المستخدمين عليه** (نقطة بيع في محلٍّ يستخدمها أكثر من موظف)، وليس نظاماً سحابياً متعدد الأجهزة. هذا الحد ليس تقليصاً بل هو نطاق الموجة الثانية كما تعرّفها الخارطة؛ المزامنة السحابية S1 مؤجلة بقرار منتج موثق في ROADMAP، وعندما تعود ستعيد النظر في نفس نموذج الهوية هذا بالوراثة لا بالإلغاء. وبناءً عليه كل التصميم هنا يفترض: مستخدمون متعددون **على الجهاز الواحد**، كل واحد برمز PIN خاص به (نفس بنية PIN الحالي)، وهوية الجلسة تحمل حتى يُقفل التطبيق، وكل حدث يُنسب لمستخدمه في `audit_log`.

والخلاصة التي يقوم عليها التصميم كله: **البنية الأمنية القائمة ليست عائقاً بل هي الميزة المؤسِّسة** — `PinVault` يغلّف بصمة الهاش بمفتاح AES-256-GCM داخل AndroidKeyStore بفشل مغلق، و`LockoutGuard` يفرض قفل تصاعدي على المحاولات، و`BiometricGate` يفتح ببصمة صاحب الجهاز. كل ما نحتاجه هو تعميم هذه الوحدة من «مستخدم واحد بمفتاحين» إلى «N مستخدمين بمفاتيح N» بنفس العقد تماماً — لا اختراع طبقة أمنية جديدة، بل إعادة تسمية ما هو موجود أصلاً.

## 2) نموذج الأدوار — أربعة أدوار، بلا صلاحيات حرة في الموجة الأولى

اخترنا **أدواراً ثابتة مسماة** لا مصفوفة صلاحيات حرة (custom permissions) في هذه الموجة، لأربعة أسباب تناسب حجم المنتج وقاعدة مستخدميه: (أ) القراءة أسرع — صاحب البقالة يفهم «كاشير/مدير» فوراً ويربكه جدول صلاحيات من 40 خانة؛ (ب) الاختبار محدود محدوداً — 4 أدوار × 27 شاشة مصفوفة قابلة للفحص الشامل، أما الفضاء الحري فلا يُفحص إلا عينات؛ (ج) الواجهة لا تحتاج شاشة «محرر صلاحيات» أصلاً في هذه الموجة؛ (د) الترقية اللاحقة نحو صلاحيات حرة تتم بتعميم الجدول نفسه (انظر §5). الأدوار الأربعة:

| الدور | الثابت | نطاقه العملي في SuperBiz |
|---|---|---|
| **المالك (Owner)** | `0` | كل شيء + إدارة المستخدمين والأدوار + حذف/أرشفة نهائية + تصدير النسخ الاحتياطية + بيانات ZATCA الرسمية |
| **المدير (Manager)** | `1` | كل التشغيل والاطلاع (تقارير، أرباح، مخزون، ذمم) — **بلا** إدارة مستخدمين وبلا عمليات الحذف النهائية وبلا تغيير بيانات المالك الضريبية |
| **المحاسب (Accountant)** | `2` | التقارير والإقرار الضريبي والفواتير وPDF والبريد — **بلا** بيع نقطة بيع ولا تعديل مخزون ولا أسعار |
| **الكاشير (Cashier)** | `3` | نقطة البيع والفواتير الجديدة والطباعة والولاء — **بلا** تقارير أرباح ولا كلفة أصناف ولا إعدادات (يرى لقطة التقارير بواجهة «بدون أرباح» تُحدد لاحقاً إن طلب السوق — الموجة الأولى تُخفي التبويب) |

قاعدة الحسم عند التعارض: **الأدنى يرى ما يخدم وظيفته فقط، ولا يُمنح إلا بوضوح** — أي أن الإعداد الافتراضي لكل شاشة/عملية هو «محرَّم على الكاشير» ثم يُرفع صراحة في جدول §3، لا العكس. هذا يقلل مساحة الخطأ الأمني ويعني أن أي باب جديد يُبنى لاحقاً (ولوحة KPIs من W1 مثلاً) يبدأ مقفولاً على غير المالك والمدير حتى يُقرر غير ذلك بقرار موثق — وهو نمط «الافتراض مغلق» الذي اتبعه المستودع أصلاً في ProEntitlement.

## 3) مصفوفة الصلاحيات مقابل الشاشات والعمليات الفعلية

المصفوفة تُقيَّد على العمليات الحقيقية الموثقة (الشاشات الـ27 + العمليات الحرجة بالكود)، لا على قائمة نظرية:

| العملية/الشاشة | Owner | Manager | Accountant | Cashier |
|---|---|---|---|---|
| نقطة البيع وإنشاء فاتورة | ✓ | ✓ | ✗ | ✓ |
| طباعة/QR/مشاركة فاتورة قائمة | ✓ | ✓ | ✓ | ✓ |
| إلغاء فاتورة (تحويلها ملغاة) | ✓ | ✓ | ✓ | ✗ |
| تعديل بيانات طرف/منتج | ✓ | ✓ | ✗ | ✗ |
| **حذف منتج/طرف نهائياً** | ✓ | ✗ | ✗ | ✗ |
| المخزون والجرد وتحركاته | ✓ | ✓ | ✗ | جرد قراءة فقط |
| التقارير المالية الكاملة (ربح/كلفة) + KPI Board | ✓ | ✓ | ✓ | ✗ |
| الإقرار الضريبي وشاشة ZATCA (بيانات المالك) | ✓ | ✗ | قراءة الإقرار فقط | ✗ |
| المصروفات والشيكات والأقساط | ✓ | ✓ | ✓ | ✗ |
| الإعدادات العامة (ضريبة/عملة/طابعات) | ✓ | ✓ | ✗ | ✗ |
| **إدارة المستخدمين والأدوار** | ✓ | ✗ | ✗ | ✗ |
| النسخ الاحتياطي/الاستعادة | ✓ | ✗ | ✗ | ✗ |
| تفعيل Pro / شراء / استعادة | ✓ | ✗ | ✗ | ✗ |
| الولاء والكوبونات (إنشاء قاعدة) | ✓ | ✓ | ✗ | تطبيق فقط |

التطبيق في الكود يمر عبر نقطة تحقق واحدة جديدة `RoleGate.require(context, Op)` حيث `Op` ثابت مُسمَّى من هذه المصفوفة — ونقاط الاستدعاء الأولى (الموجة الأولى: 14 عملية من الجدول أعلاه تتعلق بحذف/تقارير/إعدادات/مستخدمين) موزعة في VMs لا في Composables، فبوابة الدور تعمل فوق VM وتُختبر JVM بمحاكاة أدوار (نمط الاختبارات القائم بلا جهاز).

## 4) المخطط v13 — جداول جديدة فقط، وترحيل ذرّي إلحاقي

### 4.1 الجداول المضافة (عقد «إنشاء فقط لا يلمس قائماً» — عين 11→12)

```sql
-- 1) المستخدمون: هوية الجهاز المحلي (لا كلمات مرور عارية — بصمات مغلّفة كـ PinVault)
CREATE TABLE users (
  id INTEGER PRIMARY KEY AUTOINCREMENT NOT NULL,
  name TEXT NOT NULL,
  role INTEGER NOT NULL DEFAULT 3,            -- ثابت الدور (§2)، الافتراض الأقل
  active INTEGER NOT NULL DEFAULT 1,
  createdAt INTEGER NOT NULL,
  lastSeenAt INTEGER NOT NULL DEFAULT 0
);

-- 2) أسرار الدخول: نفس صيغة PinVault حرفياً لكل مستخدم
CREATE TABLE user_secrets (
  userId INTEGER PRIMARY KEY NOT NULL,
  pinWrapped TEXT NOT NULL,                   -- "ks:<ivHex>:<ctHex>" (عقد PinVault)
  biometricAllowed INTEGER NOT NULL DEFAULT 0,-- المالك فقط افتراضاً
  FOREIGN KEY(userId) REFERENCES users(id) ON DELETE CASCADE
);

-- 3) عمودَا نسبة الأثر في audit_log (إلحاق عمود بقيمة افتراضية آمنة = NULL)
ALTER TABLE audit_log ADD COLUMN actorId INTEGER NULL;   -- NULL = الحدث قبل v13 / نظام
ALTER TABLE audit_log ADD COLUMN actorRole INTEGER NULL; -- لقطة الدور لحظة الحدث (لا join)
```

ثلاث قرارات تصميمية مثبتة هنا: **أولاً** لا جدول `permissions` في v13 أصلاً — المصفوفة ثابتة في الكود (sealed class/enum بفحصاتها)، والجدول يبقى مقترحاً لموجة الصلاحيات الحرة إن طلبها السوق (§5)، فنوفر على أنفسنا أعمدة لن تُقرأ. **ثانياً** `pinWrapped` بنفس صيغة `PinVault.encrypt` الحالية — معنى ذلك أن وحدة `PinVault` نفسها تُعمَّم من مفتاح ثابت واحد (`superbiz_pin_master_v1`) إلى مفتاح alias لكل مستخدم (`superbiz_pin_u<id>`) دون تغيير العقد البايتي، واختباراتها القائمة تبقى صحيحة لآخر مستخدم تُستدعى به. **ثالثاً** أعمدة `audit_log` تُضاف بـ`ALTER` لاصقة بقيمة NULL افتراضية — عمليات الإلحاق هذه آمنة SQLite إلحاقياً، وNULL دلالته «قبل التبني» — وهي نفس دلالة `nullable` في Room بلا أي إعادة كتابة صفوف، فالترحيل ذرّي إلحاقي خالص.

### 4.2 خطوات الترحيل وترتيبها الذرّي (MIGRATION 12→13)

1. `CREATE TABLE users` + `CREATE TABLE user_secrets` (+ فهارسهما) — إنشاء فقط.
2. `ALTER TABLE audit_log` بإضافة العمودين بقيم NULL — إلحاق أعمدة فقط.
3. **زرع المالك الافتراضي داخل نفس المعاملة:** إن كان الجدول فارغاً تُدرج صف «المالك» بـ`pinWrapped` منقوله من مخزن PIN القائم (نفس `ks:` صيغة — النقل نسخ نص لا إعادة تشفير، والمفتاح في Keystore لا يُمس)؛ وإن كان مخزن PIN فارغاً (لا حماية قائمة) يُزرع المالك بلا PIN و`user_secrets` لا صف له — أول دخول بعد الترقية يسأل إنشاء PIN للمالك. **بلا سيناريو ثالث:** وجود صفوف users مسبقاً مستحيل بنيوياً لأن الجدول جديد.
4. لا تعديل لأي عمود قائم، لا إعادة تسمية، لا حذف — **صفر صف يُعاد كتابته في كل المخطط عدا سطر المالك المزروع**.

**لماذا هذا ترحيل «ذرّي» فعلاً لا اسمياً:** كل الخطوات الأربع داخل `MIGRATION` كائن واحد بمهمة `execSQL` متتالية ضمن المعاملة التي يشغّلها Room تلقائياً للمهاجر — فأي فشل في منتصفها يعيد قاعدة v12 كما كانت بلا حالة نصفية ممكنة، ولا توجد خطوة خارج المعاملة إطلاقاً (لا DataStore هنا، لا ملفات، لا Keystore: زرع المالك نسخ نص داخلي). هذا هو معنى الذرّية التي تشترطها الخطة، ونقارنها بالتصميم البديل الذي رفضناه: فصل ترحيل RBAC عن ترحيل ZATCA في ترحيلين متتاليين (13 و14) — رُفض لأنه يضاعف مخاطر الترقية على العميل لغاية صفر وظيفي، فالجداول الجديدة في الحالتين لا تتعارض، والمستخدم يستحق ترقية واحدة متقنة بدل اثنتين مرتبكتين (وهو ما صرّحت به خطة ZATCA2 §2: «الترحيلان يُنفَّذان معاً في v13»).

### 4.3 عقد عدم كسر — ما لا يُسمح لهذا الترحيل بلمسه

هذا القسم جزء من مواصفة المهمة لا زينة توثيقية، وفاحص مراجعته في PR إلزامي: (1) **كل الاختبارات 1444 الحالية تبقى خضراء بلا تعديل اختبار واحد** — الترحيل إلحاقي فلا عقد قائم يتغير؛ استثناء وحيد مسموح معلناً: اختبارات الدخول التي تحصل على المستخدم الوحيد (زرع المالك) قد تحتاج تهيئة سياق مستخدم — تُعدَّل بقرار موثق لا بصمت. (2) سلاسل strings تظل متقاسمة (`strings-guard`)؛ تُضاف مفاتيح RBAC الجديدة للغتين معاً في نفس الـPR. (3) لا وحدة نقية في `domain/` تكتسب اعتماد Android جديد للسبب — منطق الأدوار نفسه (`RoleGate`، فحص الدور) نقية JVM. (4) `allowBackup=false` وقواعد `data_extraction_rules` لا تُمس — جداول الهوية الجديدة تخضع لنفس سياسة عدم النسخ تلقائياً. (5) نسخ البيانات الاحتياطية القائمة (JSON/Excel من موجات سابقة) تعمل كما هي — RBAC لا يغير شكلها في الموجة الأولى (النسبة بين المستخدمين ميزة موجة تالية).

## 5) الترقية المستقبلية — ما صممناه عمداً كي يسهل لاحقاً

تصميم v13 يترك ثلاثة أبواب مفتوحة عمداً بلا كلفة اليوم: **(أ) صلاحيات حرة** — عند الحاجة يُضاف جدول `role_permissions(roleId, op, allow)` وتتحول قراءة `RoleGate` من فحص مصفوفة الكود إلى فحص الجدول مع الافتراض الكودي كـseed أولي؛ الواجهة `RoleGate.require` نفسها لا تتغير لأنها العقد المستهلك. **(ب) هوية موظف أغنى** — أعمدة `users` (رمز موظف للفاتورة، توقيع، راتب) تُضاف ALTER إلحاقياً بلا مساس بجداول v13 نفسها. **(ج) هوية سحابية عند عودة S1** — `users.id` المحلي يبقى هوية العرض المحلية، وتُضاف عمود `remoteId` لاحقاً بنفس النمط الإلحاقي؛ لا إعادة تصميم لأن التصميم لم يفترض المركزية يوماً. هذه الترقيات الثلاث هي الترتيب الطبيعي لموجات WS-F القادمة إذا أثبت السوق الطلب — وكل واحدة منها مستقلة وموثقة بـADR مصغر خاص حين يأتي موعدها، لا قبلها.

## 6) خطة الاختبار والقبول — كيف نعرف أنها سليمة قبل النشر

قائمة القبول المثبتة للموجة (تُختبر بالترتيب على CI ثم جهاز مرجعي): (1) اختبار ترحيل E2E على قاعدة v12 حقيقية ممتلئة ببيانات الموجات السابقة — يفتح، يزرع المالك، يقرأ كل الجداول القائمة سليمة، ويُقارن عدّ الصفوف قبل/بعد مطابقة عدا صفر فرق (زرع المالك سطر واحد معلن). (2) ترقية تراكبية من APK حقيقي قديم (نفس بند قبول الموجة W1) — تثبيت فوق V 1.0.0 ثم فحص القاعدة. (3) اختبارات JVM لـ`RoleGate` تغطي كل خلية من مصفوفة §3 (4 أدوار × 14 عملية = 56 حالة موثقة بالاسم). (4) قفل تصاعدي يعمل **لكل مستخدم** على حدة (`LockoutGuard` مُعمَّم بمفتاح userId) ويُنسب فشل الدخول في audit_log لاسمه. (5) أسرار المستخدمين لا تخرج في أي نسخة احتياطية أو استخراج بيانات (فحص data_extraction_rules + جولة adb backup على جهاز). (6) الدخول ببصمة للمالك فقط يعمل على الجهاز المرجعي، وغيره يُطلب منه PIN. (7) CHANGELOG + docs/PRIVACY_POLICY (لا تغيير في قائمة جمع البيانات — RBAC محلي خالص) محدثان في نفس الـPR.
